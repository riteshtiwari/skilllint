# SkillLint — Project Ground Rules

These rules apply to every task in this project. They are not suggestions.

---

## 1. Expert Review Is Mandatory

### Before implementing any plan:

Run all three expert reviewers in parallel against the plan and any relevant existing code.

```
reviewers/code-reviewer.md     — code quality, React patterns, security, performance
reviewers/arch-reviewer.md     — system design, cost model, auth, data model, dependencies
reviewers/test-reviewer.md     — bugs, failure scenarios, edge cases, missing error handling
```

Do not start writing code until all three reviews are complete and critical issues are addressed. If a plan has CRITICAL findings, update the plan to resolve them first, then re-review the changed sections.

### Before pushing any commit:

Run the commit reviewer against the full diff.

```
reviewers/commit-reviewer.md  — build/test gate, commit message quality, human writing check
```

A push is blocked until the commit reviewer returns APPROVED.

---

## 2. Build and Test Before Every Commit

Before any commit is created:

1. Run `npm run build` — must exit 0, no errors
2. Run `npm run lint` — no new errors introduced
3. If tests exist: run them, all must pass
4. Verify the dev server starts cleanly: `npm run dev`

Do not commit broken code. Do not commit code that produces build warnings indicating broken behavior. Fix first, commit after.

---

## 3. Always Rebase, Never Merge

- Branches must be rebased on top of `main` before pushing
- No merge commits in branch history
- Use `git rebase main` not `git merge main`
- Verify clean history with `git log --oneline main..HEAD`

---

## 4. Commit Message Standards

Every commit message must comply with `reviewers/human-writing-rules.md`.

**Required:**
- Imperative verb first: Fix, Add, Remove, Refactor, Update, Extract
- First line under 72 characters
- Describes what changed and why — not which files were touched

**Forbidden:**
- Claude, Anthropic, AI, model names anywhere in the message
- "Co-Authored-By: Claude" or any AI attribution line
- Emoji of any kind
- "This commit...", "Here we...", "We have..."
- Passive construction: "Error handling was added" → "Add error handling"
- Bullet lists in the message body
- Vague summaries: "misc fixes", "update stuff", "changes"

---

## 5. No AI Attribution

- No "Co-Authored-By: Claude" lines in commits
- No "Generated by Claude Code" or similar in any file
- No mention of AI authorship in comments, docs, or UI text
- Code and copy should read as written by a person

---

## 6. Human Writing Only

All user-facing text (UI copy, error messages, labels), code comments, and documentation must follow `reviewers/human-writing-rules.md`.

Quick reference:
- No affirmation openers (Certainly!, Absolutely!, Great!)
- No bot vocabulary: leverage, utilize, seamlessly, robust, delve into, cutting-edge
- No decorative emoji in text or comments
- No passive-voice instructions
- No three-part list conclusions
- Active voice, direct sentences, specific language

---

## 7. No Cheap Emoji

Emoji are not used in:
- Commit messages
- Code comments
- Documentation
- UI copy (unless a user-visible functional indicator)

The decorative emoji that signal "bot-generated output" are banned: ✅ ❌ 🚀 💡 🎯 🔥 ✨ 🎉 🤖 👇 👆

---

## 8. Tech Stack (locked)

```
Frontend:    Vite + React
Auth:        Clerk (Google + email)
API Proxy:   Vercel Edge Functions
Database:    Supabase (PostgreSQL)
Deployment:  Vercel
Fonts:       DM Sans + JetBrains Mono
```

Do not introduce new dependencies without explicit discussion. Do not switch any of these for alternatives without explicit discussion.

---

## 9. Design System (locked)

Colors, typography, spacing, and component rules are defined in Section 19 of `SKILLLINT_PLAN.md`. Every new component must follow them. Do not introduce new colors, fonts, or spacing values. Do not use Tailwind or any CSS framework — inline styles only, matching the existing pattern.

---

## 10. Build Order

Follow the 40-step build order in Section 22 of `SKILLLINT_PLAN.md`. Do not skip steps. Do not implement Wave 2 or Wave 3 features before Wave 1 is complete and deployed.
